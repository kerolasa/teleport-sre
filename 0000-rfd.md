## API structure

The `kind` cluster will set up a `service` that exposes the API via a
`gateway`.  This should allow one to reach the service from a browser on the
developer workstation at a loopback address.

The namespace query parameter may be spelled as either `ns` or `namespace`.
Both are accepted synonyms, and they behave identically.

The examples below assume the client certificate and key that `make certs`
generates, and they use `-k` because the CA is not in the system trust store.

| Method | URI | Description | Response
| ------ | --- | ----------- | --------
| GET | / | Project root page.  Browser friendly, used while developing. |
                                           Development time web UI for
                                           convenience, see
                                           [UI and UX](#ui-and-ux).
| GET | /list | List available kubernetes namespaces and deployments | See
                                           JSON output [List 1](#list-1).
| GET | /list?ns=namespace | List available kubernetes deployments in a
                                           specific namespace
                                           | See JSON output [List 2](#list-2).
| GET | /deployment?deployment=name&ns=namespace | Get the kubernetes Deployment
                                           replica count.  Omitting `deployment`
                                           will report all deployments
                                           within namespace.  Omitting the
                                           `ns` will report deployments in
                                           all namespaces.
                                           | See JSON output [GET
                                            Deployment](#get-deployment).
| PUT | /deployment?deployment=name&ns=namespace&replicas=N | Set the number of
                                           kubernetes Deployment replicas.  The
                                           `deployment`, `ns`, and `replicas`
                                           arguments are all required.
                                           | See JSON output [PUT
                                            Deployment](#put-deployment).

### Errors

Errors carry an HTTP status code, and a JSON body with a single `error`
field.

```
{"error":"deployment coredns not found in namespace kube-system"}
```

| Code | Reason
| ---- | ------
| 400 | A required parameter is missing, or `replicas` is not a non-negative integer.
| 401 | The client did not present a certificate signed by the cluster CA.
| 404 | The namespace or deployment does not exist.
| 500 | The kubernetes API is unreachable, or the informer cache has not synced.

## Caching

The `/list` and `GET /deployment` responses can be cached.  Caching is done
in the controller-runtime application memory.  This means that with multiple
instances it is possible to get inconsistent responses.  Inconsistency
should be reasonably unlikely due to the cache invalidation triggered by a
kubernetes Deployment watch.

The cache is populated at startup, and requests are always served from the
cache for maximum responsiveness.  While the cache is being populated, the
readiness probe will not report the pod as ready.

## Pod Lifecycle

The controller-runtime will perform graceful startup and shutdown sequences.
This means not announcing the service as alive when it is not alive, and
handling termination by waiting for in-flight requests to complete within the
grace period.  There is no intention to use lifecycle hooks.

The controller-runtime will implement a `/_heartbeat` status page that will
inform kubernetes if the controller has fully started, and is still running.
This allows adding lightweight `livenessProbe` and `readinessProbe` to the
Deployment.  The heartbeat probe informs the controller whether it can
internally determine that it is running.  HTTP/200 means all is good; any
other status code, or a missing response, means the pod is not running
correctly.

Apart from having a status page, there is a need for `restartPolicy: Always`
to have a better chance for no disruptions to the service if and when
something minor goes wrong, like an OOMKilled container or such.

Updates will use the `RollingUpdate` strategy to avoid upgrade related
disruptions, and to allow a smooth rollback, if and when the next version
turns out to be suboptimal.  Rolling upgrade is expected to work due to the
facts; the controller runs with multiple replicas, and the `Service` in
front of them performs load balancing across the replicas.  A failed upgrade
will need to revert to the previous ReplicaSet.

The controller will run in a failure tolerant manner in a single kubernetes
`kind` cluster.  Considering that the controller reports replica counts for a
cluster, there is no point in making it fault tolerant beyond the scope of a
kubernetes cluster.

## TLS Configuration

The controller will handle TLS termination.  The accepted TLS version is
1.3, and the certificates use Ed25519 with the TLS_AES_128_GCM_SHA256 cipher
suite.

Connections between the caller and the API are secured with mTLS.  The
server certificate is issued for `localhost` and `127.0.0.1`, and the caller
must present a client certificate signed by the same cluster CA.  A caller
without a valid client certificate is rejected before the request is served.

This implies a gateway in front of the service acting as a dumb TCP load
balancer.

Private and public keys, including the client certificate and key, are
created using `make certs`.

## Workflow

### How to contribute

Use `git remote -v` to see where you cloned the repository.  Use GitHub for
bugs and pull requests.  If the contributions address a vulnerability that
must be kept confidential, please use the `git format-patch main..your-branch`
tooling to attach these changes as an email sent to the upstream maintainer(s).

### Building and testing

Run `make build` or `make test`.  Running `make` without argument(s) will
output the make targets.

The `make test` will find the `_test.go` files, and run all the tests.  The
test also includes `go vet`, `gofmt`, and `golangci-lint run` checks.

## Releasing

Run `make release`.

Running `make release` will:

1. Create annotated git tag.
2. Build the controller image.
3. Request the local `kind` kubernetes cluster to perform the update.

Please note that running a release does not mean it will succeed.  One
must look for possible `make` failures, and keep an eye on service health.

## Observability

The controller will write structured logs that can be seen in stderr.
These logs can be easily fed to Elasticsearch or such.  Notice that the
configuration file has a loglevel setting.

There is also a Prometheus endpoint, that uses prefix `teleport` for the
controller specific metrics.  Primary use of these metrics is to have easy
way to tell if application has worked without issue.  Assuming during
development nothing appears to be slow Prometheus will not be used for
performance metrics.

Ideally the controller should integrate with OpenTelemetry, but this is out
of scope for quick & dirty work that did not require production quality
observability.

### Additional web listen

In addition to the API, there is an additional HTTP listener, that is not
encrypted and not reachable via the gateway.  These URIs are for
administrative purposes only, and they listen on port 9443.

| Method | URI | Description | Response
| ------ | --- | ----------- | --------
| GET | /metrics | Prometheus metrics | Prometheus output.
| GET | /_heartbeat | A page that prints OK if the controller is alive |
                                           HTTP/200 when all is working,
                                           HTTP/500 if the informer cache has
                                           not synced or the kubernetes API is
                                           unreachable, or timeout when the
                                           controller is entirely unresponsive.
| GET | /version | A page that contains the controller version | Debugging
                                           URL to see which version is running.

## Operational instructions

Interactions with kubernetes are meant to be purposefully fragile.  If
something even smells strange, the tooling will stop and inform the user what
seems to be wrong.  In these cases, one needs to debug with `kubectl` what is
going on.  There is no standard answer to how to fix the service in all
situations, but at least you should

* Check the controller logs
* Are the metrics telling you anything useful; `curl http://<pod>:9443/metrics`
* Is there a blocking network policy
  * Note.  I know challenge did not specify network policy, and my helm
    stuff might not even have them.  Point of checking network policy is the
    history I have with them; more than a few times it has been the network
    policy, to the point I am now very early on in all debug cases asking
    'are you sure it is not the network policy?'
* Is the deployment pending for a dependency, or in a restart loop?
* Have a look at `docker ps`, is the kindest/kind-control-plane container running?
* What is your computer doing, check `journalctl -b`

When nothing else helps, there is `make nuke-it-from-the-orbit` that will
wipe off all the things from kubernetes.  This is a last resort.

# client-go

The `client-go` is a simple command-line tool which will interact with the
controller.  Its `-namespace` flag maps to the `ns` or `namespace` query
parameter, `-get` maps to `GET /deployment`, and `-set` maps to
`PUT /deployment`.  The usage output of this tool is expected to be the
following.

```
$ ./client-go --help
Usage: ./client-go [options]
  -list
        List namespaces and deployments. Use -namespace to narrow down listing
  -namespace ns
        Narrow down operation to specific namespace
  -deployment name
        Narrow down operation to specific deployment
  -get
        Get number of replicas
  -set
        Set number of replicas. Requires use of -namespace and -deployment
```

# UI and UX

The controller is reachable from loopback with a browser.  If time allows,
there will be a very basic web UI that allows one to do the HTTP calls
graphically rather than with `curl`.  This comes with a strong promise
_not_ to deliver it.

If the UI is delivered, the mTLS client certificate needs to be imported into
the certificate store, which is a bit of a fiddly operation and different
browsers / operating systems need different instructions.  I am starting to
feel this feature creep is not happening.
